# تطبيق الجوال — أعراس اليمن

تطبيق واحد للطرفين: العميل ومقدّم الخدمة. الدور اختيارُ عرضٍ يُبدَّل من شاشة
الحساب، لا هويةٌ تُثبَّت عند التسجيل — الشخص نفسه قد يحجز لعرس أخيه ويبيع خدمة
التصوير.

مبنيّ على **Expo (React Native)**، بنفس اللغة والأنواع المستعملة في لوحة التحكم.

## التشغيل

```bash
cd mobile
npm install
cp .env.example .env      # املأ رابط Supabase والمفتاح publishable
npm start                 # ثم امسح رمز QR بتطبيق Expo Go على جوالك
```

**بلا ‎.env‎ يعمل التطبيق ببيانات تجريبية** — تتصفّح الشاشات كلها بلا خادم. وهو
الوضع الذي رُوجعت به الشاشات هنا.

`npm run web` يفتحه في المتصفّح: أسرع لمراجعة التخطيط، لكن قياسات الخطوط فيه
تختلف قليلاً عن الجهاز — فما يُحسم بصرياً يُحسم على جهاز.

## البناء والنشر

البناء يجري في سحابة Expo فلا يحتاج جهازك:

```bash
npx eas build --platform android --profile preview   # ملف APK للتجربة
npx eas build --platform all --profile production    # للمتاجر
```

النشر في المتاجر يحتاج حساب Apple (99$ سنوياً) وحساب Google Play (25$ مرة واحدة).

## قواعد ثابتة

**الكتابة كلها تمرّ بدوال `api_*` لا بالجداول.** الخادم هو من يحسب السعر
والعربون والعمولة وسلّم الإلغاء. لو قبِل سعراً من التطبيق لأمكن حجز قاعة بريال
واحد. راجع `supabase/README.md` لقائمة الدوال.

**المفتاح في ‎.env‎ هو publishable وحده.** مصمَّمٌ ليعيش في الأجهزة: التطبيق
المنشور يمكن فكّه واستخراج ما فيه، فالحماية في سياسات RLS لا في إخفاء المفتاح.
ولا يُوضع `service_role` هنا أبداً — يتجاوز السياسات كلها.

**التخطيط يميني.** على الأجهزة يُطلب `I18nManager.forceRTL` مرةً عند الإقلاع،
وعلى الويب لا يُطلب: react-native-web يقلب بالـ`dir` فيقلبه الطلب مرتين. والنصّ
اللاتيني (البريد، التاريخ، الرمز) يُترك من اليسار وإلا تبعثرت رموزه.

## ما لم يُبنَ بعد

- رفع مستندات التوثيق من التطبيق (الحاوية جاهزة في `supabase/storage.sql`)
- إضافة الخدمات وتسعيرها من تطبيق مقدّم الخدمة — تُدار من اللوحة حالياً
- الإشعارات الفورية (تحتاج `expo-notifications` ومفاتيح المتاجر)
- الدفع عبر البوابة — `api_confirm_payment` تنتظر خطّاف البوابة
