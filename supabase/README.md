# قاعدة البيانات والـ API — منصة حجوزات وتجهيز الأعراس

هذا المجلد هو **الخادم كاملاً**: قاعدة البيانات، وطبقة الصلاحيات، والـ API الذي يستدعيه
تطبيق العميل وتطبيق مقدّم الخدمة. لا يوجد خادم منفصل — منطق العمل يعيش داخل قاعدة البيانات
كدوال، وSupabase يعرضها عبر HTTP.

## التثبيت على مشروع جديد

**الطريق القصير — لصقة واحدة.** افتح **Supabase ← SQL Editor ← New query**، والصق
`install.sql` كاملاً، ثم Run. الملف يجمع الثلاثة الأولى أدناه بالترتيب الصحيح، وإعادة
تشغيله آمنة (كل عبارة `if not exists` أو `create or replace`).

ثم:

1. **أنشئ حساب المسؤول**: Authentication ← Users ← Add user، مع تفعيل *Auto Confirm User*.
2. **امنحه الصلاحية**: بدّل البريد في `bootstrap_admin.sql` ونفّذه. من ليس له صف في
   `admins` لا يدخل اللوحة أصلاً — وهذا ما يمنع العميل ومقدّم الخدمة من الوصول إليها.
3. **بيانات تجريبية** (اختياري، وللتصفّح فقط): نفّذ `seed.sql`. لا تشغّله على بيانات حقيقية.
4. **نفّذ `apply.sql`** — لصقة ثانية بعد `seed.sql`. تضيف طرق العرض التي تقرأ منها
   ست شاشات في اللوحة (التقييمات، مقدّمو الخدمة، الكتالوج، التسويات، الحملات، الخطط)
   وقسم «الطبخ والضيافة». بدونها تلك الشاشات تعرض خطأ `relation … does not exist`.
   وبما أن `seed.sql` يحذف الأقسام ويعيد إدخالها، فأي إعادة تشغيل له تستوجب إعادة
   تشغيل `apply.sql` بعده.
5. **اربط اللوحة**: انسخ `.env.example` إلى `.env` واملأ:

   ```
   VITE_SUPABASE_URL=https://<project-ref>.supabase.co
   VITE_SUPABASE_ANON_KEY=<publishable key>
   ```

   المفتاح المطلوب هو **publishable / anon** وحده — وهو مصمَّم للعمل في المتصفح لأن RLS
   هي ما يحمي البيانات لا سرّية المفتاح. لا تضع `service_role` ولا كلمة مرور قاعدة
   البيانات في `.env`: كلاهما يتجاوز RLS تماماً، وملفات الواجهة تصل إلى كل من يفتح الموقع.
   بمجرد وجود المتغيّرين تتحوّل كل الشاشات من البيانات التجريبية إلى مشروعك، بلا أي تعديل في الكود.

### الملفات

| # | الملف | ماذا يفعل |
| --- | --- | --- |
| — | `install.sql` | الملفات ١–٣ مجموعة في لصقة واحدة |
| 1 | `schema.sql` | الجداول والقيود والفهارس، وتفعيل RLS |
| 2 | `policies.sql` | من يرى ماذا ومن يعدّل ماذا، ومنح الصلاحيات |
| 3 | `api.sql` | دوال الـ API وطرق العرض |
| 4 | `bootstrap_admin.sql` | تعيين أول مسؤول (بعد إنشاء حسابه) |
| 5 | `seed.sql` | بيانات تجريبية (اختياري) |
| 6 | `apply.sql` | طرق عرض اللوحة + قسم الطبخ — **بعد `seed.sql`** |
| 7 | `storage.sql` | حاوية مستندات التوثيق وسياساتها (خاصة) |

## من يصل إلى ماذا

```
                    ┌──────────────────┐
تطبيق العميل ───────►│                  │
                    │   Supabase       │──► قاعدة البيانات
تطبيق مقدّم الخدمة ──►│  (RLS + دوال)   │    (RLS يفلتر كل استعلام)
                    │                  │
لوحة التحكم ────────►│                  │
                    └──────────────────┘
```

| الطرف | ما يراه |
| --- | --- |
| زائر (`anon`) | الأقسام، المحافظات، مقدّمي الخدمة الموثّقين، خدماتهم، التقييمات المنشورة |
| العميل | كل ما سبق + حجوزاته ومدفوعاته وخططه ومحادثاته هو **فقط** |
| مقدّم الخدمة | ملفه وخدماته وحجوزاته ومستحقاته ومستنداته هو **فقط** |
| المسؤول | كل شيء. ولوحة التحكم له وحده — لا يصلها عميل ولا مقدّم خدمة |

**RLS هو جدار الحماية، لا التطبيق.** التطبيق يمكن تعديله أو انتحاله؛ سياسات قاعدة البيانات لا.

## الـ API

### دوال العميل

| الدالة | ماذا تفعل |
| --- | --- |
| `api_register_profile(full_name, phone, governorate, platform)` | يربط حساب المصادقة بملف في المنصة. يُستدعى مرة بعد أول دخول |
| `api_create_booking(service_id, event_date, event_time, plan_id, guests, address, notes, pay_full)` | ينشئ حجزاً ودفعة معلّقة. **الخادم** يحسب السعر والعربون والعمولة |
| `api_cancel_booking(booking_id, reason)` | يلغي ويحسب المسترد من سلّم السياسة المنسوخ في الحجز |
| `api_submit_review(booking_id, rating, comment)` | تقييم — بعد تنفيذ الحجز فقط |
| `api_open_dispute(booking_id, subject, description, category)` | يفتح نزاعاً على حجز يخصّه |
| `api_toggle_favourite(service_id)` | يضيف/يزيل من المفضّلة، ويعيد الحالة الجديدة |
| `api_apply_as_provider(business_name, phone, bio, governorate, category_ids)` | «أريد تقديم خدمة» — ينشئ ملفاً **قيد المراجعة** |

### دوال مقدّم الخدمة

| الدالة | ماذا تفعل |
| --- | --- |
| `api_respond_to_booking(booking_id, accept, reason)` | قبول الحجز أو رفضه. الرفض يستردّ للعميل كل ما دفع |
| `api_complete_booking(booking_id)` | تأكيد التنفيذ — وبه يُفتح باب التقييم |

### طرق العرض

| الطريقة | المحتوى |
| --- | --- |
| `v_services` | الخدمات مع مقدّمها وقسمها وسياسة إلغائها — للبحث والاستكشاف |
| `v_providers` | مقدّمو الخدمة مع أقسامهم مجمّعة |
| `v_plan_summary` | خطة العرس: الإجمالي والمدفوع والمتبقي، محسوبة من الحجوزات |

### دالة محجوزة

`api_confirm_payment(payment_id, gateway_ref, method)` — **لخطّاف بوابة الدفع وحده**، تُستدعى
بمفتاح الخدمة لا من التطبيق. صلاحيتها منزوعة عن `anon` و`authenticated` صراحةً. استدعاؤها
مرتين لا يضاعف المبلغ.

### مثال

```ts
const { data, error } = await supabase.rpc('api_create_booking', {
  p_service_id: serviceId,
  p_event_date: '2026-09-15',
  p_event_time: '20:00',
  p_guests_count: 300,
  p_address: 'حي السنينة — صنعاء',
  p_pay_full: false,          // عربون، لا سداد كامل
})
```

## لماذا المنطق في الخادم لا في التطبيق

`api_create_booking` تتلقّى معرّف الخدمة والموعد فقط — **لا السعر**. الخادم يجلبه من الجدول،
ويحسب العربون بنسبة الخدمة، والعمولة من إعدادات المنصة، وينسخ سلّم الإلغاء داخل الحجز.

لو قبِل الخادم سعراً من التطبيق، لأمكن لأي شخص أن يحجز قاعة بريال واحد.

## دورة حياة الحجز

```
العميل يختار الخدمة والموعد ← يدفع العربون أو المبلغ كاملاً
        ↓
  pending_provider ──► مقدّم الخدمة يقبل ──► confirmed ──► completed ──► تقييم
        │                    │                  │
        │                    └► rejected        └► cancelled (استرداد بالسلّم)
        │                       (استرداد كامل)
        └► expired
```

عند القبول يحدث ثلاثة أشياء معاً: يُغلق اليوم في تقويم مقدّم الخدمة، وتُصدَر فاتورة، ويصل
العميل إشعار.

## سياسات الإلغاء

سلّم تنازلي بصيغة JSON — كلما اقترب الموعد قلّت النسبة:

```json
[{"hours_before": 168, "refund_percent": 100},
 {"hours_before": 48,  "refund_percent": 50},
 {"hours_before": 0,   "refund_percent": 0}]
```

**السلّم يُنسخ داخل الحجز وقت إنشائه.** تعديل السياسة لاحقاً لا يغيّر شروط حجز قائم — العميل
وافق على شروط بعينها. ودالة `refundable_amount(booking_id)` تحسب المسترد لو أُلغي الآن.

## الاختبارات

```bash
cd supabase/tests
npm install
node integrity.test.mjs   # تماسك البيانات والقيود
node api.test.mjs         # السيناريو كاملاً بهويات حقيقية
node apply.test.mjs       # apply.sql: يعمل، ويعيد التشغيل، ويصمد بعد تغيّر المخطط
node storage.test.mjs     # الحاوية خاصة وسياساتها تشير إلى دوال موجودة
```

تُشغَّل على Postgres حقيقي داخل الذاكرة (PGlite) بلا خادم ولا حساب. `api.test.mjs` يمثّل
عميلاً ومقدّم خدمة ومسؤولاً بأدوار `authenticated` الفعلية — لا كمالك الجداول، لأن Postgres
يعفي المالك من RLS فلا يثبت الاختبار شيئاً.

ما يفحصه: أن مقدّم الخدمة لا يوثّق نفسه، وأن العميل يرى حجزه وحده، وأنه لا يقبل حجزه بنفسه،
وأن العربون والعمولة تُحسبان في الخادم، وأن الاسترداد يتبع السلّم، وأن التعديل المباشر على
المبالغ لا يطال صفاً واحداً.

## ثلاثة أخطاء وجدها الاختبار

مذكورة هنا لأنها تتكرّر في كل مشروع Postgres:

1. **`can_write()` كانت تُرجع `NULL` لغير المسؤول** لا `false`، لأن `NULL in (...)` تُنتج `NULL`.
   فصارت `not can_write()` قيمتها `NULL`، وشرطٌ قيمته `NULL` لا يتحقّق — فمرّ من كان يجب منعه.
   الحل: `coalesce(..., false)`.

2. **`provider_id <> as_prov`** تُنتج `NULL` حين لا يكون المتصل مقدّم خدمة، فيمرّ الفحص.
   الحل: `is distinct from`.

3. **حارس مقدّم الخدمة كان يمنع المنصة نفسها** من تحديث عدّاداته بعد إتمام حجز. الحل: علم
   داخلي محلّي المعاملة ترفعه دوال الـ API وحدها.
