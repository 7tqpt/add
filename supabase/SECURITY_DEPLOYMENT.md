# نشر إصلاحات المراجعة الأمنية

هذه تغييرات مصدرية؛ لا تصبح حماية للبيئة الحية حتى تُطبّق على مشروع Supabase الصحيح.
خذ نسخة احتياطية قابلة للاستعادة، واختبر الترحيل على نسخة تجريبية أولاً.
لا تشغّل `seed.sql` أو تعيد التثبيت الأساسي على الإنتاج بغرض تطبيق الإصلاح.

## قبل النشر

يفترض الترحيل وجود ميزات `support.sql`، `roles.sql`، `profile.sql`،
`service_media.sql`، `chat.sql`، `chat_media.sql`، `payments_app.sql`،
`availability.sql`، `plan_tasks.sql`، `coupons.sql`، `phone_verify.sql`.
لا يعيد الترحيل ضبط مصفوفة أدوار الإدارة، ولا يستبدل مسار إتمام الحجز
في `completion_review.sql`. راجع الميزات المفقودة قبل تشغيل ملفاتها؛ لا تعِد
تشغيل `roles.sql` عشوائياً على مصفوفة صلاحيات مخصّصة.

افحص تعارض الحجوزات بهذا الاستعلام للقراءة فقط:

```sql
select provider_id, event_date, count(*) as confirmed_count, array_agg(id) as booking_ids
from public.bookings
where status = 'confirmed' and provider_id is not null
group by provider_id, event_date
having count(*) > 1;
```

إذا أعاد صفوفاً، راجع أصحاب الحجوزات وحدّد المعالجة المناسبة قبل النشر؛
الترحيل يرفض التعارض ولا يحذف حجوزات أو يلغيها تلقائياً.
الفهرس يفرض حجزاً مؤكداً واحداً لكل مزوّد في اليوم، اتساقاً مع تقويم التطبيق الحالي.

## التطبيق

شغّل `security_hardening.sql` كاملاً في SQL Editor بصلاحية إدارة القاعدة،
**بعد** ملفات الميزات. يحتوي معاملة واحدة قابلة لإعادة التشغيل؛ أي خطأ يمنع اعتماد
التغييرات. لا تشغّل ملفات SQL من إصدار سابق بعده. قد يحتاج إنشاء الفهرس إلى
نافذة صيانة عند كِبَر جدول الحجوزات.

الترحيل يمنع التعديل المباشر على حالة الحساب وتوثيق الهاتف، ويُبقي التسجيل
وتعديل الملف عبر RPC. يحصر عمليات المال والحجوزات والدعم بحسب مجال الإدارة،
ويمنع الكتابة المباشرة في التوافر وإعادة فتح يوم محجوز.

عند تفعيل `require_phone_verification`، يصبح التحقق مطلوباً في الخادم للوصول
إلى البيانات الخاصة والعمليات المرتبطة بالحساب، لا في الواجهة فقط. يبقى الملف
ومسار OTP متاحين للاسترداد، والكتالوج العام متاحاً. لا يفعّل الترحيل هذا الإعداد
تلقائياً ولا يغيّر قيمته الحالية؛ تحقق من عمل خدمة الرسائل قبل تفعيله.

سجل التدقيق يُكتب من تغييرات الجداول الفعلية للمسؤول، بهوية من `auth.uid()`.
تُهمل إدخالات السجل المباشرة من العميل للتوافق مع الواجهة الحالية. يحتفظ
السجل بأسماء الحقول المتغيرة دون نسخ قيم الرسائل أو المستندات. هذا لا يوثّق
عمليات القراءة أو محاولات الرفض، ولا يعزل مالك القاعدة أو مفتاح `service_role`؛
يلزم إبقاء سجلات Supabase وحماية مفاتيح الخادم بشكل مستقل.

إصلاحات الإشعارات السابقة لها خطواتها المنفصلة في ملفات النشر الخاصة بها؛
هذا الترحيل لا ينشر Edge Functions ولا يضبط أسرار webhook.

## التحقق

```bash
cd supabase/tests
npm install
node --test security_hardening.test.mjs
node ../../tool/controls_security.mjs
npm test
```

بعد التجربة، اختبر بحسابات منفصلة: تسجيل جديد، تعديل ملف، طلب OTP،
مزوّد يقبل حجزاً مدفوعاً، مالية تؤكد دفعة، دعم يجيب تذكرة، ومشاهد يحاول
الكتابة. يجب رفض تغيير الحالة الذاتية، العمليات المالية من الدعم،
حجزين مؤكدين في اليوم نفسه، وإدخال سجل باسم شخص آخر.

لا تُعد الصلاحيات الواسعة القديمة عند فشل اختبار تشغيل؛ أصلح التوافق على
بيئة التجربة ثم أعد الترحيل. أمان الشيفرة لا يغني عن فحص إعدادات الإنتاج
ومفاتيحه وسياسات التخزين الفعلية.
